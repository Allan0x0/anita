Chapter 31

Measuring speed

Two guides can walk a tour group from the hotel to the falls. One knows a shortcut and always takes the same six minutes. The other checks every side street, so with twice the group he takes twice as long, and with ten times the group he takes ten times as long. On a tiny group you cannot tell them apart. Fill a whole bus and the difference is the whole afternoon. Measuring the speed of an algorithm is exactly this question: not "how fast on today's small input" but "how does the time grow as the input grows". That growth is what Big-O captures, and it is what the exam asks you to name.

Asymptotic analysis means judging an algorithm by how its running time grows as the input gets large, and ignoring everything that does not affect that growth. "Asymptotic" is just a long word for "as the input heads toward big". We drop three things on purpose:

  • Constant factors. Whether each step takes 2 nanoseconds or 20 does not change the shape of the growth, so we drop the multiplier. 3n and n both count as n.
  • Lower-order terms. In n² + n, once n is large the n² dwarfs the n, so we keep only n².
  • Small inputs. We care about the trend for large n, not the wobble when n is 3.

Why throw away real detail? Because it is the growth that decides whether your program still works when the data gets ten times bigger. A slower constant you can fix with a faster machine; a worse growth curve you cannot outrun.

Big-O (the ceiling). We write O(f(n)) to say the running time grows no faster than f(n), up to a constant factor, once n is large. It is an upper bound: a promise that the cost will not climb worse than this shape. When people say "this algorithm is O(n)" they mean the work grows in proportion to the input in the worst case.

To read Big-O off code, count how many times the innermost work runs as a function of n, then keep only the fastest-growing term and drop its constant. A single pass over n items is O(n). Here is that single pass as a running program that also counts its own steps.

#include <iostream>
#include <vector>

// Linear scan: look at every element once. Cost grows like n, so O(n).
int countSteps(const std::vector<int>& items, int target) {
    int steps = 0;
    for (int x : items) {   // this loop body runs n times
        ++steps;
        if (x == target) break;
    }
    return steps;
}

int main() {
    std::vector<int> menu = {5, 9, 2, 7, 4, 1, 8};
    std::cout << "worst-case steps: " << countSteps(menu, 42) << '\n';
    std::cout << "n = " << menu.size() << '\n';
    return 0;
}

Build it

Save as scan.cpp, then compile and run:

g++ -std=c++17 scan.cpp -o scan && ./scan

Add items to the vector and rerun. The worst-case step count tracks the number of items one for one: that one-for-one growth is what O(n) names.

Big-Omega and Big-Theta. Big-O is only the ceiling. Two partners finish the picture:

  • Big-Omega, written Ω(f(n)): the floor. The running time grows at least this fast for large n. It is a lower bound, the best case you cannot beat.
  • Big-Theta, written Θ(f(n)): the tight fit. The time grows exactly like f(n), both no faster and no slower, because the same shape is both the ceiling and the floor. When O and Ω agree, you get Θ.

Picture the tour again. The shortcut guide is Θ(1): fastest case and slowest case are both flat, so the fit is tight. The street-checking guide scanning a list for one name is O(n) in the worst case (the name is last or missing) but Ω(1) in the best case (the name is first), so his ceiling and floor differ and there is no single Θ.

Reading a nested loop. When one loop sits inside another and both run n times, the inner body runs n × n times, which is O(n²). This is the classic pairwise pattern: compare every guest with every other guest, check every seat against every table. Count it and see.

#include <iostream>
#include <string>
#include <vector>

// For every pair of guests, print whether they can share a table.
// Outer loop runs n times; inner loop runs n times; body runs n*n times => O(n^2).
int main() {
    std::vector<std::string> guests = {"Ada", "Ben", "Cy", "Di"};
    long long pairs = 0;

    for (std::size_t i = 0; i < guests.size(); ++i) {
        for (std::size_t j = 0; j < guests.size(); ++j) {
            ++pairs;   // this line runs n * n times
        }
    }

    long long n = guests.size();
    std::cout << "n = " << n << '\n';
    std::cout << "inner-body runs: " << pairs << " (= n*n)\n";
    return 0;
}

Build it

Save as pairs.cpp, then compile and run:

g++ -std=c++17 pairs.cpp -o pairs && ./pairs

With 4 guests the body runs 16 times; with 8 guests it runs 64. Double the input, quadruple the work. That squaring is the signature of O(n²).

The cost of the structures you already know. Most of the exam is naming these from memory. Here is the table for the data structures and algorithms from earlier chapters, worst case unless noted.

Two patterns carry most marks: halving the problem each step gives log n, and a loop inside a loop over the same data gives n².

Challenge (name the cost)

A cook prices a set menu. The loop below walks the dishes once, and for each dish walks the same list of dishes once more to find a cheaper pairing. Before reading on, name the Big-O and say why.

for (std::size_t i = 0; i < dishes.size(); ++i) {
    for (std::size_t j = 0; j < dishes.size(); ++j) {
        consider(dishes[i], dishes[j]);
    }
}

(Answer: O(n²). The outer loop runs n times, and for each of those the inner loop runs n times, so consider is called n × n times. Doubling the menu quadruples the work.)

Q1. Explain what Big-O notation measures, using a practical example.

Model answer

Big-O notation describes how the running time (or memory) of an algorithm grows as the size of the input, n, grows. It is an upper bound: it names the worst-case growth rate, ignoring constant factors and lower-order terms, so that we compare algorithms by how they scale rather than by exact timings on one machine.

Practical example: searching a guest list of n names one by one for a booking. In the worst case the name is last or missing, so you check all n names. Double the list and you double the checks; ten times the list, ten times the checks. The work grows in direct proportion to n, so the search is O(n). If instead the list were sorted and you used binary search, each step would halve the remaining names, giving O(log n), which grows far more slowly and is why sorted data is worth keeping.

Q2. State the time complexity of the following code in terms of Big-O and justify your answer.

for (int i = 0; i < n; ++i) {
    for (int j = 0; j < n; ++j) {
        std::cout << i * j << '\n';
    }
}

Model answer

The complexity is O(n²).

Justification: the outer loop runs n times, once for each value of i from 0 to n - 1. For every single one of those iterations, the inner loop runs its own full n times. The body (the print statement) therefore executes n × n = n² times in total. Keeping only the fastest-growing term and dropping constants, that is O(n²). As a check: at n = 10 the body runs 100 times, and at n = 20 it runs 400 times, so doubling the input quadruples the work, which is the tell-tale sign of quadratic growth.

Q3. Define Big-O, Big-Omega, and Big-Theta, and explain how they relate.

Model answer

  • Big-O, O(f(n)): an upper bound. The running time grows no faster than f(n) (up to a constant factor) for large n. It names the worst case.
  • Big-Omega, Ω(f(n)): a lower bound. The running time grows at least as fast as f(n) for large n. It names the best case you cannot beat.
  • Big-Theta, Θ(f(n)): a tight bound. The running time grows exactly like f(n), because f(n) is both its upper and its lower bound.

Relation: Θ is the combination of the other two. When an algorithm is both O(f(n)) and Ω(f(n)) for the same f, its ceiling and floor meet, so it is Θ(f(n)). Example: a linear scan of an unsorted list is O(n) in the worst case (target last or absent) but Ω(1) in the best case (target first); since these differ there is no single Θ. A loop that always visits all n items with no early exit is Θ(n), because best and worst case are both n.

Q4. What is asymptotic analysis, and why do we ignore constant factors and lower-order terms when we use it?

Model answer

Asymptotic analysis studies how an algorithm's cost behaves as the input size n grows toward large values, rather than measuring an exact time for one fixed input. It gives the growth rate, which is what we express with Big-O, Big-Omega, and Big-Theta.

We drop constant factors because they depend on the machine, the compiler, and small implementation choices, not on the algorithm's shape; a step that takes 2 or 20 nanoseconds does not change whether the total grows linearly or quadratically. We drop lower-order terms because, once n is large, the fastest-growing term dominates: in n² + 100n + 500 the n² term overwhelms the rest, so we call it O(n²). The point is to compare how algorithms scale, and only the leading term decides whether a program still copes when the data gets ten times bigger.

Q5. Give the worst-case time complexity of each of the following, with a one-line reason: (a) accessing an array element by its index, (b) searching an unsorted linked list for a value, (c) binary search on a sorted array.

Model answer

  • (a) O(1). An array element's address is computed directly from the index, so it takes the same constant time regardless of the array's size.
  • (b) O(n). A linked list has no index; you follow the links from the head, and in the worst case the value is at the end or absent, so you visit all n nodes.
  • (c) O(log n). Binary search discards half of the remaining range at each step, so the number of steps is how many times n can be halved, which is log n.
