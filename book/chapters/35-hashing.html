Chapter 35

Hash Tables

Walk into a busy hotel and hand over your coat. The clerk does not search a pile; he reads your ticket number, walks straight to that one numbered hook, and hangs the coat. Later you give the same number and he walks to the same hook. No searching, no scanning down a list, just a number that points at a place. A hash table is that coat-check built in code: turn a key (a name, a word, a room) into a number, and use the number to jump straight to where the value lives.

A hash table is an array of slots (call them buckets) plus a rule for deciding which bucket a key belongs to. That rule is the hash function: it takes a key and returns a bucket index, a plain integer in range. Store a value by hashing its key to an index and dropping it in that bucket; retrieve it by hashing the same key again and looking in the same bucket.

The whole point is speed. A linked list or unsorted array makes you walk item by item, slow when there are many items. A hash table skips the walk: the hash function computes the address directly, so a lookup takes about the same short time whether the table holds ten items or ten thousand. That near-constant lookup time, written O(1) on average, is why hash tables sit under dictionaries, database indexes, and the symbol tables inside compilers.

A good hash function has two jobs: it must always send the same key to the same bucket (or you could never find anything again), and it should spread different keys evenly across the buckets so no single bucket gets crowded. A common simple one for text keys adds up the character codes and takes the remainder modulo the table size, so the answer always lands inside the array.

Here is a small table that maps a dish name to its price. It builds the array of buckets, hashes each key, and reads one back. This version uses chaining (explained just below) so that two dishes landing in the same bucket can both live there.

#include <iostream>
#include <string>
#include <vector>
#include <list>

const int SIZE = 7;

// Hash function: sum the character codes, then wrap into range.
int hashKey(const std::string& key) {
    int sum = 0;
    for (char c : key) sum += c;
    return sum % SIZE;
}

int main() {
    // Each bucket is a list of (name, price) pairs.
    std::vector<std::list<std::pair<std::string, int>>> table(SIZE);

    // store: hash the key, drop the pair in that bucket.
    auto store = [&](const std::string& name, int price) {
        table[hashKey(name)].push_back({name, price});
    };

    // retrieve: hash the key, scan only that one bucket.
    auto price = [&](const std::string& name) -> int {
        for (const auto& entry : table[hashKey(name)])
            if (entry.first == name) return entry.second;
        return -1; // not found
    };

    store("sadza", 3);
    store("rice", 2);
    store("beef", 5);

    std::cout << "beef costs " << price("beef") << '\n';
    std::cout << "rice lives in bucket " << hashKey("rice") << '\n';
    return 0;
}

Collisions. A hash function squeezes a huge range of possible keys into a small range of buckets, so sooner or later two different keys hash to the same index. That clash is a collision. It is not a bug, and you cannot avoid it in general; you just need a rule for what to do. Two standard rules exist.

  • Chaining (separate chaining): each bucket holds a small list, and colliding keys just get appended to that bucket's list. To find a key, hash to its bucket then walk that short list. This is what the menu program above does: the bucket is a std::list.
  • Open addressing: every key lives directly in the array, one per slot. On a collision you probe for another slot by a fixed rule. The simplest is linear probing: if the slot is taken, step to the next slot, and the next, wrapping around, until you find a free one. Lookup repeats the same walk until it finds the key or an empty slot.

Open addressing keeps everything in one flat array, no lists. Here is linear probing storing tourist-site names. On a clash it steps forward to the next free slot; a lookup retraces those steps.

#include <iostream>
#include <string>

const int SIZE = 7;
std::string slot[SIZE];
bool used[SIZE] = { false };

int hashKey(const std::string& key) {
    int sum = 0;
    for (char c : key) sum += c;
    return sum % SIZE;
}

// store: on a clash, step forward until a free slot appears.
void store(const std::string& key) {
    int i = hashKey(key);
    while (used[i]) i = (i + 1) % SIZE; // linear probe
    slot[i] = key;
    used[i] = true;
}

// find: retrace the same probe walk; stop at the key or an empty slot.
int find(const std::string& key) {
    int i = hashKey(key);
    int steps = 0;
    while (used[i] && steps < SIZE) {
        if (slot[i] == key) return i;
        i = (i + 1) % SIZE;
        ++steps;
    }
    return -1; // not found
}

int main() {
    store("victoria");
    store("kariba");
    store("nyanga");

    std::cout << "kariba sits in slot " << find("kariba") << '\n';
    std::cout << "hwange found? " << (find("hwange") != -1 ? "yes" : "no") << '\n';
    return 0;
}

Pros and cons. A hash table's strength is speed: store, retrieve, and delete all run in about O(1) time on average, far faster than walking a list or array. Its costs are the flip side of that trick.

  • Good: average constant-time lookup, store, and delete; simple idea; ideal for "find by key" work like dictionaries and caches.
  • Bad: no order is kept, so you cannot read the keys out sorted or ask for the smallest without scanning everything. Worst-case lookup degrades to O(n) if many keys collide into one bucket (a bad hash function, or a table too full). It needs spare room to stay fast, so it trades memory for speed, and picking a good hash function and table size takes care.

The load factor (items divided by buckets) is the dial: keep it low and buckets stay short and fast; let it climb toward full and collisions pile up. Real libraries grow the table and rehash everything once the load factor passes a threshold, roughly 0.7 for open addressing.

For the missing name, find keeps probing 4, 5, 6 and only stops when it hits an empty slot or has checked every slot; since none match, it returns -1. This is why open addressing must never leave the table completely full: with no empty slot, a failed search has to walk the whole array.)

Q1. What is a hash table, and what is the role of the hash function within it?

Model answer

A hash table is a data structure that stores key-value pairs in an array of slots called buckets, and gives near constant-time (O(1) average) store and retrieve by key. Instead of searching through the items, it computes where each item belongs.

The hash function is what computes that location: it takes a key and returns a bucket index, an integer within the array's range (for example, by summing the key's character codes and taking the remainder modulo the table size). Its role is to map every key to a bucket so that storing hashes the key to pick a slot, and retrieving hashes the same key to look in the same slot. A good hash function is consistent (the same key always gives the same index) and spreads keys evenly across the buckets to keep collisions rare.

Q2. A collision happens when two keys hash to the same bucket. Describe two techniques for resolving collisions.

Model answer

1. Chaining (separate chaining). Each bucket holds a list of entries. When two keys hash to the same bucket, both are kept in that bucket's list. To store, hash the key and append to the bucket's list; to retrieve, hash the key and scan only that one short list. The array never fills up, because each bucket can grow, though very long chains slow lookups down.

2. Open addressing. Every entry is stored directly in the array, one per slot. When the target slot is taken, the algorithm probes for another slot by a fixed rule. In linear probing, it steps to the next slot (wrapping around the end) until it finds a free one; storing places the key in the first free slot found, and retrieving retraces the same steps until it finds the key or reaches an empty slot. This uses no extra lists, but the table must keep some free slots or it slows to a full scan.

A lookup for guava hashes the key, gets bucket 3, then walks that bucket's list comparing keys: it passes mango (no match) and reaches guava (match). Only the entries in bucket 3 are ever examined, not the whole table, which is why the search stays fast as long as chains stay short.

Q4. State two advantages and two disadvantages of a hash table.

Model answer

Advantages:

  • Very fast average lookup, insertion, and deletion by key: about O(1), independent of how many items the table holds.
  • Simple and natural for "find the value for this key" tasks, such as dictionaries, caches, and database indexes.

Disadvantages:

  • No ordering is kept, so you cannot list keys in sorted order or find the smallest or largest without scanning everything.
  • Performance depends on a good hash function and spare capacity: many collisions (a poor hash function or a table too full) degrade lookups to O(n), and keeping the table fast means using extra memory.
