The Saw-Queue

Unit 6: Stacks. Unit 7: Queues. Two lines with one rule each. A queue serves the job that has waited longest: first in, first out. A stack always takes the piece on top: last in, first out. Push, pop, enqueue and dequeue all cost O(1).

Day 1 · The stack

Last in, first out: push and pop on top only

A stack is a pile you only touch from the top. Drop an offcut on the pile with push; take the top one off with pop. You cannot reach the middle or the bottom without popping everything above it first.

Because only the top ever moves, both push and pop are single steps: O(1). The piece that went on last is the one that comes off first, so a stack is LIFO (last in, first out).

The code

top does double duty: it is where the next push lands and how many items the stack holds. Empty is top == 0; full is top == CAP.

Day 2 · Undo with a stack

The undo stack: pop reverses your last cut

This is where a stack earns its keep. Every cut you make pushes its offcut onto an undo stack. Press undo and you pop the top: the most recent cut, undone first.

Because pop always takes the last thing pushed, the undo order is the exact reverse of the cut order. Cut 0.4, 1.1, 0.7 and undo hands them back 0.7, 1.1, 0.4. That reversal is LIFO made useful, and each push or pop is still O(1).

The code

Nothing about undo needs a search or a sort. The stack already stores cuts in the exact order to reverse them: newest on top.

Build it

Run it. Then, after two undos, cut one new offcut and undo again; confirm the new cut comes back before the older ones.

Day 3 · The queue

First in, first out: join the back, leave the front

A queue is a line, like saw-jobs waiting to be cut. A new job joins at the back with enqueue. The saw takes the next job from the front with dequeue. Two ends, each with one job.

The job that has waited longest is served next, so a queue is FIFO (first in, first out). Track the front with head and the back with tail; moving either is one step, so enqueue and dequeue are O(1).

The code

A stack touches one end for both moves; a queue splits the work across two, so the oldest item leaves while the newest arrives at the far side.

Day 4 · The circular queue

Wrap the ends with % CAP to reuse freed slots

The Day 3 queue has a leak of space. Every dequeue moves head forward and never back, so the slots it passes go dead. Enqueue a few, dequeue a few, and tail hits the end of the array while empty slots sit unused at the front.

A circular queue fixes this by wrapping: after the last slot, the next index is 0 again, computed with % CAP (the remainder operator). A count field tells full from empty, since head == tail now means both. Still O(1), no wasted space.

The code

(tail + 1) % CAP is the whole trick: for CAP = 4 it counts 0, 1, 2, 3, 0, 1, ... forever, so the freed front slots get reused instead of stranded.

Build it

Run it. Then print head and tail after each call and watch tail jump from 3 back to 0.

Day 5 · Saw-job scheduler

Process saw-jobs in arrival order with a queue

Here is the queue's real build step. Each saw-job is a struct: an id and a length to cut. Jobs are enqueued as they arrive; the scheduler dequeues them one by one and cuts each.

Because a queue is FIFO, the processing order is exactly the arrival order. No job jumps the line, no job is starved: whoever waited longest gets cut next. That fairness is the reason a scheduler reaches for a queue and not a stack.

Day 6 · Tie it together

Stack vs queue: an honest trade-off

Neither structure is "better"; they hand data back in opposite orders, and you pick by which order the job needs. A stack reverses (last in, first out); a queue preserves (first in, first out). Both cost O(1) per operation, so the choice is about order, not speed.
