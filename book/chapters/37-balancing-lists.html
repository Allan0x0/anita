Chapter 37

Balancing trees and better lists

You can nail a whole roof truss out of plumb: peak leaning hard to one side, every strut stacked below the last. It still stands, but it carries load badly and any repair means climbing the long crooked side. A binary search tree can lean the same way, and when it does, searching it is no faster than reading a shopping list top to bottom. This chapter is about two fixes builders reach for: keeping a tree balanced so it stays short and quick, and giving a list a second rail so you can walk it both ways and splice into it fast.

Why a BST needs balancing. A binary search tree is fast only when it is short. Each step of a search throws away one side of the tree, so a search costs about the height of the tree, not the number of nodes. If the tree is bushy and short, height grows like log n, and a thousand nodes are five or ten steps deep. Fast.

But the shape depends entirely on the order you insert. Feed a BST values that are already sorted, say 10, 20, 30, 40, 50, and every value is larger than the last, so every one goes right. The tree stops being a tree in any useful sense: it is a straight line leaning right, height n, one long crooked rafter. Searching it is now a linear scan, O(n), the very slowness the tree was meant to beat.

A balanced tree keeps the two sides of every node close to the same height, so the whole thing stays about log n tall no matter what order the values arrive in.

How you keep it balanced. You do not eyeball it. A plain BST cannot fix its own shape, so we use a self-balancing tree: one that watches its height as you insert and delete, and quietly re-shapes itself to stay short. The re-shaping move is a rotation, a small local swap that lifts one node up and pushes its parent down, like re-hanging a strut on the joint above it. The order of the values never changes, only the shape.

Two families of self-balancing BST are worth knowing by name:

  • AVL tree: after every insert or delete it checks each node and rotates so the two subtrees never differ in height by more than one. Strict, so it stays very short and searches are quick.
  • Red-Black tree: a looser scheme that allows a bit more lopsidedness but does less re-shaping work per change. It is the one the C++ standard library uses under std::map and std::set, so you have been using a balanced tree all along.

The Red-Black tree. A Red-Black tree is a binary search tree where every node carries one extra bit of paint: it is either red or black. The colours are not decoration; they are a bookkeeping trick that forces the tree to stay roughly balanced without the strict height check an AVL tree does. Five rules (the Red-Black properties) hold at all times:

  • Every node is red or black. One colour bit per node, nothing else.
  • The root is black. The top of the tree is always black.
  • Every leaf is black. The empty null ends of the tree count as black leaves.
  • A red node has black children. So you can never have two reds in a row on any path (no red parent with a red child).
  • Equal black height. Every path from a given node down to any leaf below it passes through the same number of black nodes.

Those last two rules are the whole point. The equal-black-height rule sets a baseline length for every downward path, and the no-two-reds rule says the longest path can be at most twice the shortest (reds can only pad a path, and never two in a row). A path that is at most twice another cannot lean into a line, so the tree's height stays O(log n), and search, insert, and delete are all O(log n). When an insert or delete breaks a rule, the tree repairs itself by recolouring nodes and doing a rotation or two, then carries on.

The doubly linked list. A plain (singly) linked list, from the earlier chapter, gives each node one pointer: next. You can only walk forward. A doubly linked list gives each node two pointers: next to the node ahead and prev to the node behind. Now the chain is a set of rafters bolted on both ends, and you can walk it either direction.

That second rail buys real things over a singly linked list:

  • Walk backward. From any node you can step to the one before it, so you can read the list in reverse without starting over from the head.
  • Delete in place. To remove a node in a singly list you first have to find the node before it (walk from the head again). In a doubly list the node already knows its prev, so you can unhook it in one move.
  • Splice either side. Given a node, you can insert a new one before or after it directly, because you can reach both neighbours.

The cost is honest: every node carries an extra pointer (more memory), and every insert and delete has to fix up two links instead of one, so there is slightly more code to get right.

Insert at the front. Adding a node to the head of a doubly linked list is the common case (a new item jumps to the top of the pile). It is four link fixes: point the new node's next at the old head, set the old head's prev back to the new node, clear the new node's prev (it is the front now), and move head to the new node. Here is the whole thing as a runnable program.

#include <iostream>
#include <string>

struct Node {
    std::string data;
    Node* prev;
    Node* next;
};

// Insert a new node at the front of a doubly linked list.
// head is passed by reference so we can move it to the new node.
void pushFront(Node*& head, const std::string& data) {
    Node* n = new Node;
    n->data = data;
    n->prev = nullptr;      // the new node is the front, nothing before it
    n->next = head;         // it points at the old front
    if (head != nullptr) {
        head->prev = n;     // the old front now points back at the new node
    }
    head = n;              // the head is the new node
}

// Walk forward from the head, printing each value.
void printForward(Node* head) {
    for (Node* cur = head; cur != nullptr; cur = cur->next) {
        std::cout << cur->data << ' ';
    }
    std::cout << '\n';
}

int main() {
    Node* head = nullptr;
    pushFront(head, "bolts");
    pushFront(head, "ridge");
    pushFront(head, "rafter");   // most recent lands at the front

    printForward(head);          // prints: rafter ridge bolts
    return 0;
}

The circular linked list. In a singly linked list the last node points at nullptr: the chain has a definite end, and if you walk off it you fall into null. A circular linked list changes one link: the last node points back at the head instead of at null, so the chain closes into a ring. Walk it and you never reach an end; you just come back to where you started.

That ring shape suits anything that cycles: a rota of tour guides taking the next group in turn, players around a table, or a playlist set to repeat. From any node you can reach every other by going round, and there is no special end to handle. The catch is the mirror of the gain: a naive loop that waits for nullptr will spin forever, so you must stop when you arrive back at the node you began from. The listing below walks a small ring exactly once by watching for the head.

#include <iostream>

struct Node {
    int data;
    Node* next;
};

int main() {
    // Build a three-node ring by hand: 1 -> 2 -> 3 -> back to 1.
    Node* a = new Node{1, nullptr};
    Node* b = new Node{2, nullptr};
    Node* c = new Node{3, nullptr};
    a->next = b;
    b->next = c;
    c->next = a;            // the last node closes the ring

    Node* head = a;

    // Walk the ring exactly once: stop when we return to the head.
    Node* cur = head;
    do {
        std::cout << cur->data << ' ';
        cur = cur->next;
    } while (cur != head);   // NOT (cur != nullptr): a ring has no null end

    std::cout << '\n';       // prints: 1 2 3
    return 0;
}

Challenge (spot the bug)

A student copies the ring-walking loop above but writes the stop condition as a singly linked list out of habit:

Node* cur = head;
while (cur != nullptr) {
    std::cout << cur->data << ' ';
    cur = cur->next;
}

What happens when this runs on the three-node ring, and why? Fix it with one change.

(Answer: it never stops. In a circular list no node's next is ever nullptr, so cur != nullptr is always true and the loop prints 1 2 3 1 2 3 1 2 3 ... forever. Fix: stop when you get back to the head, using a do ... while (cur != head) loop as in the working listing.)

Q1. Explain why a binary search tree can become inefficient, and describe how a tree is kept balanced.

Model answer

A binary search tree searches by discarding one subtree at each step, so a search costs about the height of the tree. The shape, and therefore the height, depends on the order values are inserted. If values arrive already sorted (for example 10, 20, 30, 40), every new value is larger than the last and goes right, so the tree degenerates into a straight line of height n. Searching it is then a linear O(n) scan, no better than an unsorted list, and the advantage of the tree is lost.

A tree is kept balanced by using a self-balancing BST, which watches the heights of subtrees as nodes are inserted and deleted and re-shapes itself to stay short (height about log n). The re-shaping is done with rotations: small local moves that lift a node up and push its parent down without changing the left-smaller, right-larger ordering. AVL trees and Red-Black trees are the two common schemes. Keeping height near log n keeps search, insert, and delete at O(log n).

Q2. What is a Red-Black tree? State its properties.

Model answer

A Red-Black tree is a self-balancing binary search tree in which every node stores one extra bit of information, a colour that is either red or black. The colours are used to keep the tree approximately balanced so that its height stays O(log n) and search, insert, and delete are all O(log n). It is the structure the C++ standard library uses for std::map and std::set.

Its properties (which hold at all times) are:

  • Every node is either red or black.
  • The root is black.
  • Every leaf (the null end of a branch) is black.
  • A red node has only black children (so no two red nodes appear in a row on any path).
  • Every path from a given node down to any leaf below it contains the same number of black nodes (equal black height).

Together the last two properties guarantee that the longest root-to-leaf path is at most twice the shortest, which keeps the tree from leaning into a line and holds the height at O(log n). When an insert or delete breaks a property, the tree restores it by recolouring nodes and performing rotations.

Q3. Define a doubly linked list and give two advantages it has over a singly linked list.

Model answer

A doubly linked list is a linked list in which each node holds its data and two pointers: next, pointing to the node ahead of it, and prev, pointing to the node behind it. A singly linked list gives each node only a next pointer.

Two advantages over a singly linked list:

  • Two-way traversal. Because each node knows the node before it, the list can be walked backward as well as forward, without restarting from the head.
  • Faster deletion of a known node. To delete a node you need its predecessor; a singly list must walk from the head to find it, while a doubly list already has it in prev, so the node can be unhooked directly.

(The cost is one extra pointer per node and two links to fix on each insert or delete instead of one.)

Q4. Write a C++ function that inserts a new node at the front of a doubly linked list of integers. Explain the pointer changes it makes.

Model answer

The head is passed by reference so the function can move it to the new node.

#include <iostream>

struct Node {
    int data;
    Node* prev;
    Node* next;
};

void pushFront(Node*& head, int value) {
    Node* n = new Node;
    n->data = value;
    n->prev = nullptr;      // 1. new node is the front, nothing before it
    n->next = head;         // 2. it points at the old front
    if (head != nullptr) {
        head->prev = n;     // 3. old front points back at the new node
    }
    head = n;              // 4. head now names the new node
}

int main() {
    Node* head = nullptr;
    pushFront(head, 30);
    pushFront(head, 20);
    pushFront(head, 10);   // 10 is now at the front

    for (Node* cur = head; cur != nullptr; cur = cur->next) {
        std::cout << cur->data << ' ';   // prints: 10 20 30
    }
    std::cout << '\n';
    return 0;
}

The four numbered steps are the whole job: link the new node forward to the old head, link the old head backward to the new node (only if the list was not empty), leave the new node's prev null because it is the front, and move head to the new node.

Q5. Explain the difference between a singly linked list and a circular linked list.

Model answer

In a singly linked list each node points to the next, and the last node points to nullptr, so the list has a definite end. To visit every node you start at the head and follow next until you hit null.

In a circular linked list the last node points back to the head instead of to null, so the chain closes into a ring with no end. Starting from any node you can reach every other node by going round, and you return to where you began. Because no node's next is ever null, a traversal must stop when it comes back to its starting node rather than by testing for null; a loop that waits for nullptr would run forever. Circular lists suit things that repeat in a cycle, such as a round-robin rota or a playlist set to repeat.
