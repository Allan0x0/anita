The Sorted List

Unit 8: Sorting. Unit 9: Searching. Put the cut-list in order, then find a member fast. Simple sorts (bubble, selection) cost O(n squared); quicksort averages O(n log n). Linear search scans everything at O(n); binary search halves a sorted list each step at O(log n).

Day 1 · Bubble sort

Swap neighbours until the cut-list is in order

Bubble sort is the simplest way to order the cut-list of timber lengths. Walk the list comparing each length with the one next to it, and swap any pair that is out of order. The biggest length keeps drifting right until it settles at the end.

One walk is not enough, so you repeat the walk. Two nested loops over n lengths make this O(n squared): slow on a long list, but easy to see and to write. After the last pass the whole cut-list is sorted ascending.

The code

The inner loop stops one earlier each pass (n - 1 - i): the tail is already sorted, so there is no point re-checking it.

Day 2 · Selection sort

Find the smallest, swap it to the front, repeat

Selection sort keeps a sorted front and an unsorted tail. Each round it scans the tail for the minimum length and swaps that into the front. Grow the sorted front by one, shrink the tail, repeat until the cut-list is ordered.

It compares as much as bubble sort, so it is still O(n squared), but it does at most one swap per round instead of many. A sorted cut-list lets you pack pieces against the stock in order, leaving smaller offcuts.

The code

Bubble sort swaps on every out-of-order pair it meets; selection sort waits, finds the true minimum, and swaps just once per round.

Build it

Run it. Then add a swaps counter, increment it on each swap, and print the total: at most n - 1.

Day 3 · Quicksort

Divide and conquer: partition, then recurse

Quicksort is the fast one. Pick a pivot length, then partition the cut-list so smaller lengths sit left of the pivot and larger sit right. The pivot is now in its final place. Sort each side the same way.

This is divide-and-conquer: split the problem into two halves and recurse. Halving each level gives O(n log n) on average, which beats the O(n squared) simple sorts on a long list. Worst case is O(n squared) when the pivot is always the smallest or largest.

The code

A function that calls itself on smaller pieces is recursion. Each call handles one side of the partition until the piece has one element, which is sorted by definition.

Day 4 · Linear search

Walk the cut-list until you hit the spec

Linear search is the search that always works. Start at the front of the cut-list and check each length in turn until one matches the spec you want. No order required, so it runs on the raw, unsorted list straight off the saw.

The catch is speed: a match near the end, or no match at all, means you touch every length. That makes it O(n), growing straight with the list size. Return the index of the first match, or -1 to say it is absent.

The code

Returning -1 for "not found" is a common C idiom: a real index is never negative, so -1 can never be mistaken for a hit.

Day 5 · Binary search

Halve a sorted cut-list each step to find a length

Binary search is the reason sorting pays off. Keep a range from lo to hi and look at the middle length. If it is the target, done. If the target is larger, drop the left half; if smaller, drop the right. Each step throws away half the range.

It needs sorted input, because dropping half assumes everything past the middle is larger. Halving each step makes it O(log n), which crushes linear O(n) at scale: a million lengths take about 20 steps, not a million.

The code

Writing lo + (hi - lo) / 2 instead of (lo + hi) / 2 avoids an overflow when the two indexes are huge. The result is the same middle.

Day 6 · Tie it together

Sort once, then search fast, forever

The two units meet here. An unsorted cut-list off the saw is fine for one linear search. But if you will search it again and again, sort it once and every later search can be binary: O(log n) instead of O(n). The sort is a cost you pay once to make searching cheap.
