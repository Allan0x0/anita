Chapter 19

Searching: finding the right member

The truss bin holds a hundred steel members, each stamped with a length. The plan calls for a 300 cm chord. You could tip the whole bin out and paw through it, or you could be smart about it. Every program has the same problem: a pile of data, and one item you need out of it. How you look decides whether the search takes a blink or a coffee break. This chapter is the two ways to look, and when to use each.

Linear search: check every one

The plain way is to start at the first item and check each one until you hit the target or run off the end. This is linear search. It makes no demand on the data: the members can be in any order, any jumble. That freedom is its strength. Its weakness is speed. If the member you want is last, you touched every one to find it.

#include <iostream>

int main() {
    // member lengths in cm, in any order (a real bin is a jumble)
    int lengths[6] = {240, 180, 300, 150, 420, 360};
    int target = 300;

    int found = -1;                      // -1 means "not seen yet"
    for (int i = 0; i < 6; i++) {
        if (lengths[i] == target) {
            found = i;
            break;                       // stop at the first match
        }
    }

    if (found != -1) {
        std::cout << "Member of " << target
                  << " cm is at position " << found << std::endl;
    } else {
        std::cout << "No " << target << " cm member in the bin" << std::endl;
    }
    return 0;
}

Build it

g++ -std=c++17 search.cpp -o search && ./search

Prints Member of 300 cm is at position 2. Change target to 500 and it prints the "not in the bin" line instead. On a truss job this is your cut list check: walk the bin once, confirm the member exists before you promise it to the frame.

Binary search: cut the pile in half

If the members are sorted by length, short to long, you can do far better. Look at the middle one first. If it is too long, the one you want must be to its left, so throw away the whole right half. If it is too short, throw away the left half. Each look halves what is left. This is binary search. The catch, and it is the whole catch: the data must already be sorted. Run it on a jumbled bin and it will lie to you, reporting "not found" for a member sitting right there.

Three markers run the search. low and high are the ends of the part still in play; mid is the middle of that part. Compare the member at mid to the target. Equal means found. Too small means slide low to mid + 1. Too big means pull high to mid - 1. The window shrinks every pass until it either lands on the target or closes to nothing.

#include <iostream>

int main() {
    // members sorted short to long, lengths in cm
    int lengths[7] = {150, 180, 240, 300, 360, 420, 480};
    int target = 360;

    int low = 0;
    int high = 6;                        // last index
    int found = -1;

    while (low <= high) {
        int mid = (low + high) / 2;
        if (lengths[mid] == target) {
            found = mid;
            break;
        } else if (lengths[mid] < target) {
            low = mid + 1;               // target is in the right half
        } else {
            high = mid - 1;              // target is in the left half
        }
    }

    if (found != -1) {
        std::cout << "Found " << target
                  << " cm at position " << found << std::endl;
    } else {
        std::cout << target << " cm is not stocked" << std::endl;
    }
    return 0;
}

Build it on the truss line

g++ -std=c++17 binsearch.cpp -o binsearch && ./binsearch

Before you can search a truss member rack this way, you must build it sorted: rack the members short to long as they come off the saw. That one discipline at the rack is what earns you the fast search later. Sort once at build time, search cheaply every time after.

How fast is each?

Count the worst case, the number of members you must inspect when luck is against you. Linear search may touch all of them, so for n members it is O(n): double the bin, double the work. Binary search halves the pile each look, so it needs about log₂ n looks, written O(log n). The gap is not small. A bin of 1000 members: linear search may check 1000; binary search checks at most 10. A bin of a million: linear checks a million, binary checks 20. That is the payoff for keeping the rack sorted.

Challenge: spot the bug

A cook keeps a list of dishes by prep time and runs binary search to check whether a 25 minute dish is on it. It reports "not found", but 25 is right there. What is wrong?

#include <iostream>

int main() {
    int prep[6] = {40, 10, 25, 55, 15, 30};   // minutes
    int target = 25;

    int low = 0, high = 5, found = -1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (prep[mid] == target) { found = mid; break; }
        else if (prep[mid] < target) low = mid + 1;
        else high = mid - 1;
    }
    std::cout << (found != -1 ? "on the menu" : "not found") << std::endl;
    return 0;
}

Answer: the array is not sorted. Binary search assumes ascending order; on the jumbled list it discards the half that actually holds 25 and never sees it. The code compiles and runs, which makes the bug sneaky: the algorithm is fine, the prerequisite is broken. Fix it by sorting prep first ({10, 15, 25, 30, 40, 55}), or use linear search, which needs no order.

Challenge: predict the output

A guide lists tourist-spot entry fees, sorted low to high: {20, 35, 50, 75, 90}. Trace the binary search for target = 50. Which positions does mid take, and what prints?

Answer: low=0, high=4, so mid=2, and fees[2] is 50. Match on the first look. It prints Found 50 at position 2 after inspecting exactly one item. The middle element being the target is binary search's best case.

Exam practice

Q1. Compare linear search and binary search. State one situation where each is the better choice. (4 marks)

Model answer

Linear search checks each element in turn from the start. It works on data in any order and is simple to write. Its worst case is O(n).

Binary search repeatedly halves a sorted range, so its worst case is O(log n), far faster on large data. It cannot run on unsorted data.

Prefer linear search when the data is unsorted, or the list is small, or you search it only once (sorting first would cost more than it saves). Prefer binary search when the data is already sorted and large, or you search the same sorted list many times, so the one-off sort pays for itself.

Q2. State the prerequisite that binary search requires but linear search does not, and explain what goes wrong if it is not met. (3 marks)

Model answer

Binary search requires the data to be sorted (in a known order, normally ascending). It relies on that order to decide which half to discard: if the middle value is smaller than the target, it assumes every value to the left is also smaller and throws that half away.

On unsorted data that assumption is false, so binary search can discard the half that actually holds the target and wrongly report "not found". It still runs and gives no error, which makes the fault easy to miss. Linear search has no such requirement because it inspects every element.

Q3. Write a complete C++ program that stores the sorted array {5, 12, 18, 23, 40, 61} (recipe cook times in minutes) and uses binary search to report whether 23 minutes is present, and if so at which index. (6 marks)

Model answer

#include <iostream>

int main() {
    int times[6] = {5, 12, 18, 23, 40, 61};   // sorted, minutes
    int target = 23;

    int low = 0, high = 5, found = -1;
    while (low <= high) {
        int mid = (low + high) / 2;
        if (times[mid] == target) {
            found = mid;
            break;
        } else if (times[mid] < target) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }

    if (found != -1) {
        std::cout << target << " min found at index " << found << std::endl;
    } else {
        std::cout << target << " min not in the list" << std::endl;
    }
    return 0;
}

It prints 23 min found at index 3. The marks are for a working loop with low/high/mid, the two-way narrowing, and handling both the found and not-found cases.

Q4. State the worst-case time complexity of binary search and explain, in terms of what happens each pass, why it has that value. (4 marks)

Model answer

The worst-case complexity of binary search is O(log n) (base 2), where n is the number of elements.

Each pass compares the target with the middle element and discards half of the remaining range. So the size still in play goes n, n/2, n/4, n/8, and so on. The worst case is when the target is missing or at the very last step: the search continues until the range shrinks to a single element (or to nothing). The number of halvings needed to reduce n to 1 is log₂ n, so that many comparisons is the worst case. For n = 1,000,000 that is about 20 comparisons, against up to 1,000,000 for linear search.
